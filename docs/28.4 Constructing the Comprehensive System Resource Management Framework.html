DETAILED ANALYSIS OF THE LINUX OPERATING SYSTEM

28.4 Constructing the Comprehensive System Resource Management Framework

The baseline concepts governing Control Groups (cgroups) have been examined across preceding analyses detailing their early-stage infrastructure [17.3]. Within the Linux kernel bootstrap pipeline, the cgroup initialization process is partitioned across two distinct execution phases: the early phase (cgroup_init_early()) and the late phase (cgroup_init()). The defining technical discrepancy between them resides in their explicit execution checkpoints and absolute configuration depth. The structural purpose of early initialization is to bind critical, high-priority resource subsystems (such as cpuset) onto the primary bootstrap process contexts (PID 0 and PID 1) as early as possible [26.6, 28.3].

Conversely, cgroup_init() is executed during the late phase of the system boot sequence, a checkpoint where virtual memory management structures, multi-core page allocators, and the Virtual Filesystem (VFS) are fully online and ready [24.3, 27.6]. Its primary technical responsibility is to handle the complete initialization of all residual resource subsystems, mount the standard filesystem interfaces, register the cgroup virtual filesystems into the core VFS registries, create the explicit /sys/fs/cgroup mount points, initialize the global lookup hash tables, and expose the administrative tracking nodes at /proc/cgroups and /proc/[pid]/cgroup [27.6, 28.1]. The function is hosted within the control groups core source tree file git/kernel/cgroup/cgroup.c, and its definition is implemented as follows:

int __init cgroup_init(void)
{
	struct cgroup_subsys *ss;
	int ssid;
	BUILD_BUG_ON(CGROUP_SUBSYS_COUNT > 16);
	BUG_ON(cgroup_init_cftypes(NULL, cgroup_base_files));
	BUG_ON(cgroup_init_cftypes(NULL, cgroup1_base_files));
	cgroup_rstat_boot();
	rcu_sync_enter_start(&cgroup_threadgroup_rwsem.rss);
	get_user_ns(init_cgroup_ns.user_ns);
	mutex_lock(&cgroup_mutex);
	hash_add(css_set_table, &init_css_set.hlist, css_set_hash(init_css_set.subsys));
	BUG_ON(cgroup_setup_root(&cgrp_dfl_root, 0));
	mutex_unlock(&cgroup_mutex);
	for_each_subsys(ss, ssid) {
		if (ss->early_init) {
			struct cgroup_subsys_state *css = init_css_set.subsys[ss->id];
			css->id = cgroup_idr_alloc(&ss->css_idr, css, 1, 2, GFP_KERNEL);
			BUG_ON(css->id < 0);
		} else {
			cgroup_init_subsys(ss, false);
		}
		list_add_tail(&init_css_set.e_cset_node[ssid], &cgrp_dfl_root.cgrp.e_csets[ssid]);
		if (cgroup_disable_mask & (1 << ssid)) {
			static_branch_disable(cgroup_subsys_enabled_key[ssid]);
			printk(KERN_INFO "Disabling %s control group subsystem\n", ss->name);
			continue;
		}
		if (cgroup1_ssid_disabled(ssid))
			printk(KERN_INFO "Disabling %s control group subsystem in v1
 mounts\n", ss->name);
		cgrp_dfl_root.subsys_mask |= 1 << ss->id;
		WARN_ON(ss->implicit_on_dfl && !ss->threaded);
		if (ss->implicit_on_dfl)
			cgrp_dfl_implicit_ss_mask |= 1 << ss->id;
		else if (!ss->dfl_cftypes)
			cgrp_dfl_inhibit_ss_mask |= 1 << ss->id;
		if (ss->threaded)
			cgrp_dfl_threaded_ss_mask |= 1 << ss->id;
		if (ss->dfl_cftypes == ss->legacy_cftypes) {
			WARN_ON(cgroup_add_cftypes(ss, ss->dfl_cftypes));
		} else {
			WARN_ON(cgroup_add_dfl_cftypes(ss, ss->dfl_cftypes));
			WARN_ON(cgroup_add_legacy_cftypes(ss, ss->legacy_cftypes));
		}
		if (ss->bind)
			ss->bind(init_css_set.subsys[ssid]);
		mutex_lock(&cgroup_mutex);
		css_populate_dir(init_css_set.subsys[ssid]);
		mutex_unlock(&cgroup_mutex);
	}
	hash_del(&init_css_set.hlist);
	hash_add(css_set_table, &init_css_set.hlist,  css_set_hash(init_css_set.subsys));
	WARN_ON(sysfs_create_mount_point(fs_kobj, "cgroup"));
	WARN_ON(register_filesystem(&cgroup_fs_type));
	WARN_ON(register_filesystem(&cgroup2_fs_type));
	WARN_ON(!proc_create_single("cgroups", 0, NULL, proc_cgroupstats_show));
#ifdef CONFIG_CPUSETS
	WARN_ON(register_filesystem(&cpuset_fs_type));
#endif
	return 0;
}

This segments charts the logical execution flow of the control groups initialization routine cgroup_init() during system boot. In summary, this function achieves the following core operations:

  • Assembling the Baseline Environment:

    • Leverages BUILD_BUG_ON to assert that the aggregate subsystem count does not breach the 16-controller threshold barrier.

    • Dispatches cgroup_init_cftypes to register the control group's core unified interface files (such as cgroup.procs, etc.).

    • Spins up the centralized resource statistics (rstat) mechanism and initializes the read-write semaphore consumed during thread group synchronization.

  • Initializing Core Data Structures:

    • Fetches the validation credentials and reference counter for the initial cgroup namespace's parent user namespace.

    • Invokes cgroup_setup_root() to build the default root hierarchy tree of the control groups subsystem (the standard v2 unified root layout, cgrp_dfl_root).

    • Appends the initial control group subsystem state matrix (init_css_set, which encapsulates the operational states of all boot-phase processes) straight into the global lookup hash table (css_set_table).

  • Iterating and Activating Individual Subsystems:

    • If a specific subsystem was already bootstrapped during the early boot phase, the engine allocates its dynamic ID; otherwise, it calls cgroup_init_subsys to execute a complete configuration sweep.

    • Audits the kernel boot command-line arguments; if an administrator explicitly passed a flag to disable a controller, the routine deactivates its static key and steps over its block.

    • Evaluates the structural traits of each subsystem to determine whether it should be mapped onto a legacy v1 container versus the default v2 unified root, programming the tracking bitmasks accordingly.

    • Appends subsystem-specific control definition structures (cftypes) onto the filesystem architecture, exposing the concrete configuration knobs to user space under the directory path /sys/fs/cgroup.

    • Dispatches the callback ss->bind to anchor each subsystem to the initial process matrix.

  • Exposing Interfaces to User Space:

    • Creates the physical mount point directory for cgroup under the sysfs framework at /sys/fs/cgroup.

    • Formally registers both the cgroup (v1) and cgroup2 virtual filesystem types into the core VFS driver repositories.

    • Instantiates the virtual file /proc/cgroups to allow user-space administrative utilities to audit precisely which subsystems are natively supported by the running kernel.

The function first executes a compile-time static safety assertion via BUILD_BUG_ON(CGROUP_SUBSYS_COUNT > 16) to guarantee that the absolute volume of concurrent subsystems does not overshoot 16 [17.3]. This rigid threshold is mandatory because the core kernel utilizes a streamlined 16-bit tracking bitmap to monitor and audit the status of active subsystem controllers; allowing more than 16 controllers to be compiled into the image would cause the bitmask tracking logic to fail.

The routine leverages cgroup_init_cftypes() to initialize the generic baseline interface files that reside uniformly within all cgroup directories regardless of which specific controller owns the node, including creating the unified tracking files cgroup.procs, cgroup.threads, cgroup.subtree_control, cgroup.controllers, and notify_on_release. It alternative dispatches cgroup_init_cftypes() to populate the legacy v1 control group base interfaces. These interface files are modeled inside the kernel via the struct cftype configuration descriptor. The cftype structure defines the layout parameters of the virtual control files to be dynamically generated under the subsystem directory tree, anchoring their respective .read and .write callback handler operations. In short, it instructs the control groups framework precisely what virtual files to map out, what text names to assign them, what access permissions to enforce, and which internal kernel functions to call whenever a user application triggers a read or write transaction against the node.

The invocation of cgroup_rstat_boot() initializes the unified resource statistics framework. This infrastructure serves as the foundational, low-level execution engine consumed by control groups to handle multi-tiered resource telemetry aggregation—such as calculating process memory saturation metrics or compiling historical CPU utilization metrics [25.3, 28.3]. These telemetry data streams are systematically aggregated upward layer-by-layer throughout the tree hierarchy; conceptually, this routine functions as the master power switch activating the entire statistics subsystem.

The call rcu_sync_enter_start() forcefully drives explicit cgroup read paths to commence operations inside a slow-path synchronization mode right from the start [19.1]. This strategic configuration avoids the high processing latencies and pipelines stalls that would otherwise occur if the subsystem frequently dispatched synchronous synchronize_rcu() operations at a later stage. Because synchronize_rcu() introduces excessive temporal overhead within the control groups core, the engine prefers to route lookup paths down the un-optimized slow track initially. The cgroup architecture represents a highly dynamic environment characterized by frequent subsystem lookups, high-frequency task migrations across nodes, and continuous runtime hierarchy updates; forcing the system to block and wait out a comprehensive RCU grace period every time an internal read/write operational tracking state toggled would heavily compromise initialization velocities and system responsiveness [19.1, 21.3].

The utility get_user_ns() increments the object reference counter belonging to the parent user namespace (user_ns) that owns the initial cgroup namespace context [26.6, 27.1]. This tracking safeguard guarantees that the foundational user namespace context supporting init_cgroup_ns remains strictly anchored in memory and immune to premature deallocation loops, illustrating a widely utilized object lifecycle management paradigm integrated across the Linux kernel codebase (where pairs of matching get() and put() API loops are extensively deployed to govern object persistence).

Upon capturing the global control group mutex lock, the routine dispatches hash_add() to append the list head node address of the initial subsystem state matrix (init_css_set.hlist) into the primary tracking hash table css_set_table, calculating the target hash bucket index by passing the controller array through the transformation helper css_set_hash().

css_set_table is a high-performance global hash table deployed to index all active control group subsystem state combinations (struct css_set). Its technical purpose is to rapidly resolve an existing compiled state matrix based on the base address of an inbound array of CSS pointers, serving as a critical acceleration structure when task threads dynamically join or migrate across control groups. The acronym CSS expands to define the Cgroup Subsystem State (struct cgroup_subsys_state), which acts as the definitive data structure archiving the runtime execution state and parameters of an individual controller node bound to a specific cgroup junction. Concurrently, the css_set structure models the collective matrix of all controller states associated with a single process context (or a grouped block of parallel tasks). Because an individual process thread is authorized to simultaneously hold membership across completely separate control groups—for instance, a task can be restricted by a specific memory cgroup, governed by an independent CPU cgroup, and throttled by a separate pids cgroup—the unique combination of distinct CSS descriptors tracking these states are consolidated together to form a singular css_set fingerprint.

The initial subsystem state matrix (init_css_set) represents a global baseline configuration compiled during early boot, mapping out the default control group states allocated to the system's absolute first tracking tasks.

The function cgroup_setup_root() instantiates the default root container node cgrp_dfl_root anchoring the unified control group hierarchy tree, structuring the node via the struct cgroup_root descriptor block. The cgroup_root structure archives the critical metadata used to manage and navigate a control group hierarchy tree, encapsulating metrics including the string name assigned to the architecture tree, the specific cgroup node it represents, the unique hierarchy identification integer (ID), the aggregate volume of cgroups currently tracking along the tree branches, the bitmask mask mapping out the compiled subsystems attached to the hierarchy, and a file pointer targeting the root directory of the corresponding kernel virtual filesystem. It acts as the definitive core orchestrating cgroup tree management.

From the architectural perspective of the kernel's virtual filesystem layers, invoking cgroup_setup_root() constructs the underlying virtual framework that maps the cgroup root path /sys/fs/cgroup in memory, establishing this root container as the definitive origin point for the entire cgroup v2 unified tree hierarchy [27.6]. The operational milestones successfully fulfilled by cgroup_setup_root() primarily encompass:

  • Initializing the Reference Counters for the Target Control Group:
    This usage counter tracks and determines whether all dependent resources are correctly released before the root node is destroyed.

  • Initializing the Filesystem Root Inode and kernfs Nodes:
    The core kernel hierarchy of a cgroup is organized via kernfs nodes, which are dynamically mapped to construct the file directory tree structures and corresponding VFS inodes mounted at /sys/fs/cgroup [27.6].

  • Subsystem Re-binding:
    Guided by the passed subsystem mask (ss_mask), specified controllers (such as CPU, I/O, etc.) are unlinked from their legacy tracking hierarchies and re-bound under this newly instantiated root layer.

  • Appending the Default Root Node (cgrp_dfl_root) into the Global Kernel List cgroup_roots and Incrementing the Global Counter cgroup_root_count:
    This establishes the baseline "process-to-hierarchy" mapping architecture (link_css_set).

  • Traversing All css_set Instances Referenced by Pointers inside the css_set_table:
    Utilizing a specialized linked list of type struct cgrp_cset_link, the routine constructs a bi-directional lookup mapping bridging the control group associated with the default root node (cgrp_dfl_root.cgrp) to each traversed css_set.

Within the Linux kernel, the cgrp_cset_link structure acts as a critical intermediary connector deployed to manage the complex many-to-many (M:N) mapping relationships that bridge cgroups with css_set matrices. In a control group architecture, a single css_set can simultaneously associate with multiple distinct cgroups belonging to completely separate hierarchies; conversely, a single discrete cgroup can tie into multiple separate css_set frames (because different tasks running inside that single cgroup can independent hold memberships in alternate hierarchies).

Acting as the connective hub, cgrp_cset_link splices the two worlds together, empowering the kernel to execute high-efficiency traversals starting from either end of the mapping.

The structural tracking layout of struct cgrp_cset_link is defined as follows:

struct cgrp_cset_link {
    struct cgroup       *cgrp;
    struct css_set      *cset;
    struct list_head    cset_link;
    struct list_head    cgrp_link;
};

Within this configuration block, the cgrp and cset pointers reference the literal target control group object and CSS collection instance, respectively. The cset_link head member chains the active cgrp_cset_link node directly into the .cset_links master tracking array managed inside the target cgroup structure, enabling the kernel to instantly audit precisely which css_set entities are actively consuming that specific cgroup. Concurrently, the cgrp_link member hooks the current link structure straight into the .cgrp_links registry array managed inside the target css_set structure, allowing the kernel to take a single designated css_set and instantly resolve every control group it maps to across all available tracking hierarchies. The macro loop helper for_each_subsys() is leveraged to traverse every available control group subsystem (controller) configured across the system. The exact programmatic operations executed within this loop block have been parsed in exhaustive detail across the preceding sections and are omitted here to avoid redundancy.

Because the master default control group subsystem state set undergoes dynamic updates and modifications inside this loop framework, cgroup_init() dispatches hash_del() to temporarily extract the default subsystem state node from its early un-optimized queue slots, subsequently recalculating its hash index relative to the newly bound subsystem states to securely re-hash and commit the entry back into the global css_set_table.

The function sysfs_create_mount_point() carves out the designated sysfs mount point, constructing a physical directory container named cgroup under the parent pathway /sys/fs/. This directory functions as the central home base anchoring all subsequent cgroup hierarchical mounting frameworks [27.6].

Following the creation of this mount point, the routine calls register_filesystem() to formally register the cgroup (v1) and cgroup2 (v2) virtual filesystem formats into the VFS core registries [27.6]. Completing this registration milestone is a strict prerequisite before user-space orchestration tools can successfully execute formatting commands like mount -t cgroup ... or mount -t cgroup2 .…

The function proc_create_single() instantiates the virtual path node /proc/cgroups and registers the output formatting handler callback proc_cgroupstats_show() with the core procfs subsystem [28.1]. This setup guarantees that whenever a user-space utility executes an analytical trace like cat /proc/cgroups, the kernel dynamically hooks the event to compile and display the active subsystem statistics on the fly.

Finally, if the kernel image is compiled with explicit control set support enabled via CONFIG_CPUSETS, the routine triggers an auxiliary execution path to register the specialized cpuset virtual filesystem type, which handles isolated multi-core CPU and memory node allocations [28.3].
