DETAILED ANALYSIS OF THE LINUX OPERATING SYSTEM

27.6 Establishing Filesystem Caches

Within Linux, a filesystem is not merely a mechanism for data storage; it serves as the operational administrative core of the operating system, driven by the guiding philosophy that "everything is a file." The Virtual Filesystem (VFS) represents one of the most sophisticated designs in Linux—an architectural abstraction layer situated directly between user-space application programs and concrete, low-level filesystem implementations (such as ext4, XFS, NTFS, or NFS). Regardless of the underlying hard drive formatting, the commands utilized by users (such as ls or cp) remain uniform; the VFS assumes responsibility for translating these generalized instructions into specific low-level syntax blocks that the underlying storage controller can process.

Linux segments file storage into two distinct components: index nodes (Inodes) and data blocks (Blocks). The index node archives a file's metadata (including access permissions, owner ownership flags, byte size, creation timestamps, and the absolute physical layout coordinates of data blocks on disk), while the data blocks house the actual file contents. Every individual file across the system is assigned a unique tracking Inode number.

The Directory Entry (Dentry) records the explicit mapping bridging a literal filename to its corresponding index node number, functioning as the vital communication bridge linking filenames to physical files. This decoupled architecture explains precisely why an identical standalone file can be bound to multiple independent filenames simultaneously (the mechanism behind filesystem hard links).

Depending on the targeted deployment profile and hardware constraints, production-grade Linux environments commonly integrate the following filesystem types:

  • Ext4: Exceptionally stable and highly compatible, serving as the standard default selection for the vast majority of mainstream Linux distributions.

  • XFS: A high-performance, scalable journaling filesystem optimized to orchestrate massive files and withstand highly concurrent, multi-threaded hardware I/O workloads, routinely deployed on enterprise-grade database servers.

  • Btrfs: Supports advanced Copy-on-Write (CoW) snapshots, dynamic volume pooling, and transparent online data compression, utilized extensively as the baseline layout for modern operating system images.

  • F2FS (Flash-Friendly File System): Engineered specifically to optimize read and write operations across non-volatile flash storage architectures (such as SSDs, SD cards, and embedded mobile storage chips), significantly extending storage media longevity.

Within the Linux paradigm, interfacing with a new storage drive mandates executing a Mount operation. This configuration binds a hardware storage partition directly onto an existing directory node (the mount point) inside the system tree, empowering application threads to read and write drive contents by navigating via that targeted directory path.

The function vfs_caches_init() instantiates the specialized lookaside allocation registries within the slab layer for file-related critical data structures, while bootstrapping the core infrastructure required to handle high-speed path translation loops and file object management. The routine is hosted within the directory cache source tree file git/fs/dcache.c, and its definition is implemented as follows:

void __init vfs_caches_init(void)
{
	names_cachep = kmem_cache_create_usercopy("names_cache", PATH_MAX, 0,
		SLAB_HWCACHE_ALIGN|SLAB_PANIC, 0, PATH_MAX, NULL);
	dcache_init();
	inode_init();
	files_init();
	files_maxfiles_init();
	mnt_init();
	bdev_cache_init();
	chrdev_init();
}

The vfs_caches_init() function dispatches a call to dcache_init() to assemble the directory entry (dentry) cache framework, bootstrapping the core infrastructure that governs path resolution performance. A directory entry represents an independent string segment compiling a full filesystem pathway; for instance, the virtual file path /home/user/a.txt is programmatically decomposed into a linear chain composed of four distinct dentry blocks: /, home, user, and a.txt. All structural path resolution passes executed by the kernel are fundamentally engineered as a sequential search traversal tracking an interconnected chain of dentry objects. The microarchitectural relationship bridging literal filenames, tracking dentries, and physical filesystem nodes (represented by inodes) is illustrated in Figure 27-2.

The routine dcache_init() leverages KMEM_CACHE_USERCOPY() to construct the master dentry_cache allocation pool. To harden the system against data leakage vectors during bi-directional user-copy streams, this specialized allocator strictly configures a boundary whitelist constraint dictating that when the kernel copies memory payloads back down to user space, only the localized memory bytes housing the .d_iname array field within struct dentry are authorized for exposure; all alternative internal tracking fields are blocked from direct copy access. Upon securing this lookaside pool, the function invokes alloc_large_system_hash() to initialize a high-speed global lookaside hash table named dentry_hashtable, allowing the filesystem engine to rapidly resolve a child directory entry by cross-referencing its parent dentry address with the target name string.

Following this step, vfs_caches_init() calls inode_init() to establish the slab object allocation pool and corresponding global hash tables for index nodes, providing the structural foundation required to manage file metadata fields (permissions, sizes, and timestamps). The inode structure preserves a file's core administrative attributes, concretely describing the node layout; typical payload metrics enclose absolute file byte size, rwx access permission masks, uid/gid ownership keys, time tracking indices, physical disk block pointers, and the explicit file type classification (e.g., mapping whether the node represents a standard regular file, a directory container, or a peripheral character/block hardware device).

The function inode_init() dispatches kmem_cache_create() to instantiate a specialized lookaside repository for index nodes, constructing a dedicated object pool for struct inode entries to eliminate the performance penalty of high-frequency memory allocations and deallocations. Furthermore, it dispatches alloc_large_system_hash() to initialize the global inode lookup hash table to ensure rapid object resolution during runtime file operations.

Subsequently, vfs_caches_init() triggers files_init() to initialize the slab allocation caches for struct file instances along with the global tracking limits restricting open file descriptors, providing the structural infrastructure consumed by core system calls like open(), read(), and write().

To clarify the structural layout: while the previously initialized dcache_init() focus is to resolve path string translation bottlenecks, and inode_init() is tasked with managing physical file entities in memory, files_init() is engineered specifically to handle the runtime orchestration of active, open file instances (objects instantiated following a successful call to open()). Within the system bootstrap pipeline, files_init() assumes sole responsibility for constructing the management framework that tracks open file handles.

The kernel coordinates these open files by linking three highly critical data structures: the file table container structure (struct files_struct), the file descriptor table (struct fdtable), and the active file object descriptor (struct file). These three tracking nodes operate in a multi-tiered, hierarchical sequence to compose a comprehensive view of how a process orchestrates its open descriptors:

  • File Object (struct file): Captures and records the specific operational state resulting from an individual, successful call to open(). This structure encloses the active read/write byte offset tracker (f_pos), the access flags configuration bitmask (f_flags), and a path descriptor pointer (f_path) pointing to the underlying inode. Even if two entirely separate process threads concurrently open an identical physical file on disk, the kernel instantiates two entirely separate, decoupled file structures to track their respective sessions independently.

  • Files Struct (struct files_struct): Governs the comprehensive registry of all files opened by an individual process thread. This administrative block is embedded directly within the process's main control block (struct task_struct) and manages a tracking pointer targeting the active fdtable layout, the open file descriptor allocation bitmaps, along with a small, localized pre-allocated array of file object references (implemented as a low-level microarchitectural optimization to bypass dynamic memory allocation cycles whenever a process handles merely a small volume of parallel file references).

  • File Descriptor Table (struct fdtable): The core component inside this table is an index pointer array referencing an array of active file object pointers. Every individual cell slot within this pointer matrix houses a direct memory address referencing a target struct file descriptor, and the standard File Descriptor integer (FD) returned to user-space applications maps directly to the array's numeric index subscript. For example, when an application passes a file descriptor parameter of FD=0, the kernel's virtual memory translation layers query the 0-th index slot within this descriptor array to fetch the matching struct file reference pointer, smoothly resolving the active file context required to execute the requested I/O transaction.

The absolute microarchitectural and logical tracking relationships bridging the parent task, the files container, the descriptor arrays, and the underlying virtual filesystem structures are illustrated in the following structural layout:

Process (struct task_struct)

└── files_struct (Administrative Container)

├── fdtab (Pointer referencing the actively deployed fdtable)

└── fdtable (File Descriptor Table)

└── fd[] (Array of pointers instantiated via double pointer **fd)

├── [0] ----> struct file (Standard Input - stdin)

├── [1] ----> struct file (Standard Output - stdout)

└── [N] ----> struct file (Custom Active Open File Descriptor)

└── f_inode ----> VFS Inode (Physical File Template)

The core function files_init() dispatches kmem_cache_create() to construct a dedicated lookaside SLAB/SLUB allocation cache for file structures, optimizing the high-speed allocation and structural recycling of struct file instances. Every individual time an application thread fires an open() system call to access a filesystem node, the memory allocator extracts a clean descriptor block directly from this cached pool to record the distinct state metrics of that specific open session (such as tracking the live byte offset pointer f_pos and configuring the open access flags f_flags).

Concurrently, files_init() parses the system's aggregate physical memory size to calculate a balanced, system-wide maximum open file capacity ceiling. By proactively reserving a finite, deterministic slice of physical memory to service file descriptor objects, the kernel guarantees that extreme high-concurrency workloads can never spawn an uncontrolled volume of open file instances that would completely saturate and crash the system's general memory nodes.

In summary, the execution of files_init() bootstraps the foundational lookaside slab caches for struct file nodes and applies the global file object limit boundaries, establishing the core baseline infrastructure consumed by fundamental filesystem system calls like open() and close(). It serves as the definitive command center for open file instance management inside the VFS layer.

The companion routine files_maxfiles_init() behaves as a dedicated resource calculation engine tasked exclusively with defining system-wide maximum limits. Its central technical responsibility is to audit the aggregate physical memory capacity available across the machine and mathematically compute the absolute upper ceiling of concurrent file handles authorized to exist simultaneously within the image.

The routine mnt_init() initializes the virtual filesystem mounting mechanism and assembles the initial skeletal skeleton of the master global mount tree. Its primary operations encompass instantiating the root node of the global mount namespace (the absolute root foundation of the mount tree), allocating memory resources for the local mount caching channels, initializing the array headers of the global mount lookup hash tables, registering and mounting core virtual filesystems, and establishing the definitive starting checkpoint for the VFS directory hierarchy tree.

mnt_init() initially invokes kmem_cache_create() to carve out a dedicated lookaside allocation cache within the slab layer named "mnt_cache". Every single time a physical storage partition or virtual hardware block device is committed to a mount point across the system, the VFS core must instantiate a fresh struct mount tracking node. Deploying this dedicated lookaside pool drastically elevates memory management execution speeds during high-frequency allocation and deallocation sweeps over mount tracking nodes.

Following this allocator setup, mnt_init() dispatches alloc_large_system_hash() to initialize a high-performance global lookaside lookup table named "Mount-cache", which is optimized to execute rapid descriptor lookups targeting active struct mount instances. The mount structure acts as the definitive data node within the Virtual Filesystem (VFS) layer to describe an individual, active mounted filesystem instance while tracking its absolute coordination coordinates inside the global mount tree. By cross-referencing a parent mount point address with its corresponding target dentry, the VFS engine can evaluate this hash table to rapidly determine whether a designated file path (such as /home) behaves as an independent physical mount boundary, significantly accelerating sub-mount resolution passes.

Concurrently, mnt_init() dispatches an alternate call to alloc_large_system_hash() to carve out a separate system lookaside hash table named "Mountpoint-cache", which is engineered to manage and rapidly resolve physical mount point nodes across the kernel space. Distinct from the structural role of the "Mount-cache"—which uses a combined key fusing the "parent mount pointer + active mount dentry" to resolve a specific struct mount instance during path translation walks—the "Mountpoint-cache" is tasked exclusively with managing the physical mount points themselves, anchoring the concrete VFS directory entries (Dentries) where external file systems attach. By hashing the memory address pointers of these mount point dentries, the kernel can efficiently orchestrate mount tracking, execute unmount transformations, and continuously audit precisely how many independent filesystems are concurrently stacked over a single physical directory node.

Subsequently, mnt_init() calls the low-level routine kernfs_init(), which dispatches kmem_cache_create() to prepare the operational infrastructure and lookaside allocation pools consumed by the virtual kernfs framework. This pass constructs a dedicated lookaside slab cache named "kernfs_node_cache" tailored to house struct kernfs_node elements. Within the Linux device driver and sysfs model, every independent directory entry, hardware property, or attribute tracking file exposed under the sysfs hierarchy (such as auditing a network card's physical MAC block via the path /sys/class/net/eth0/address) maps directly to a discrete, memory-resident kernfs_node structure inside the kernel.

The most critical microarchitectural milestones orchestrated by mnt_init() are executed via the routines sysfs_init() and init_rootfs(), which build directly upon the lookaside slab caches established during the kernfs_init() phase.

  • The function sysfs_init() handles the physical creation of the absolute root directory node for the sysfs file system (the device model tracking filesystem, mounted standard at the directory path /sys) and registers the filesystem framework into the global VFS registries, opening the primary window through which the core kernel exposes its live hardware device hierarchy tree to user-space tools.

  • Concurrently, init_rootfs() initializes the temporary memory-resident root filesystem (rootfs), which acts as the system's baseline initial root mount point throughout the remainder of the system bootstrap phase. It dictates whether the internal memory disk deployed to temporarily hold and run the early boot micro-archives (initramfs or initrd) is backed by a legacy, low-efficiency ramfs layout versus being powered by a contemporary, high-performance tmpfs memory allocation scheme.

Within the Linux virtual filesystem architecture, the path /sys/fs functions as the unified configuration, status tracking, and monitoring interaction interface, serving as the master entry funnel for multiple independent filesystems, mount points, and corresponding kernel API abstractions. These control interfaces are typically grouped by specialized sub-functions and distributed across dedicated subdirectory hierarchies, such as /sys/fs/cgroup, /sys/fs/ext4, /sys/fs/f2fs, and /sys/fs/bpf. mnt_init() dispatches a call to kobject_create_and_add() to dynamically construct an active system kobject named "fs" (which instantiates the physical directory entry /sys/fs), providing a centralized parent node to serve as the master repository anchoring all subsequent filesystem-specific sysfs management interfaces.

At its conclusion, the mnt_init() function dispatches a call to shmem_init() to initialize the core shared memory (Shared Memory - shmem) and temporary ram-backed filesystem infrastructure (tmpfs / shmem). The Linux kernel exposes two completely decoupled implementation variants of shmem_init(), which are toggled at compile time based on the state of the configuration flag CONFIG_SHMEM. When CONFIG_SHMEM=y is active in the build parameters, the kernel compiles a full-featured, robust shared memory orchestration framework; conversely, if the flag is disabled, the toolchain substitutes a highly minimalist, space-optimized fallback variant designated as Tiny Shmem to accommodate tightly constrained micro-embedded systems.

For the standard implementation, the function shmem_init() initializes the shared memory filesystem (tmpfs/shmem) [July 12, 2026]. It initially constructs a dedicated slab cache pool for shared memory index nodes (inodes). Following this lookup setup, the routine registers shmem_fs_type into the core VFS registries under the filesystem type string "tmpfs". It subsequently dispatches kern_mount() to mount an internal, private tmpfs filesystem instance tracked via the global handle shm_mnt, which acts as the definitive memory backing store consumed by shared memory allocations, anonymous files, and memfd_create() tracking systems. Furthermore, if the system image is running with Transparent Huge Pages (THP) active, the routine configures the corresponding huge page allocation and fragmentation policies for this master superblock.

Within the Linux architecture, the kernel implements high-speed Inter-Processor Communication (IPC) by managing a specialized, hidden virtual filesystem dedicated to shared memory. In simple terms, the central engineering objective of the shared memory mechanism is to map an identical range of physical memory page frames into the virtual address spaces of entirely separate processes, enabling ultra-low-latency data exchange. While shared memory serves as the kernel's low-level backend memory page management engine, tmpfs acts as the user-space interaction interface layer. Whenever an administrator mounts a tmpfs instance (such as the standard system share /dev/shm), the underlying data files are stored directly inside this shared memory architecture.

Under traditional process communication paradigms—such as transferring data payloads across pipes or network sockets—the data stream must undergo repetitive copy operations moving back and forth between the kernel context and the user memory canvas. The performance advantage of shared memory stems from its ability to bypass these bottlenecks entirely; by directly mapping a single contiguous physical memory block into the page tables of multiple concurrent processes, threads can read and write the shared memory space as fast as accessing their own private heaps, entirely eliminating kernel-space context switching overhead and data copying latencies.

At its conclusion, mnt_init() dispatches init_mount_tree() to construct a temporary root directory workspace. init_mount_tree() acts as the critical bootstrap routine tasked with assembling the system's absolute first mount tree hierarchy, creating the foundational root view for all execution threads. It dispatches vfs_kern_mount() to mount a specialized, built-in root filesystem designated as rootfs, establishing the definitive logical first filesystem of the operating system. The engine then allocates the absolute first struct mount instance across the system to represent this root filesystem, making this node the root of the global mount tree. Following this deployment, init_mount_tree() instantiates the initial root namespace (init_user_ns) and links this first master mount structure directly into that namespace context. All subsequently spawned downstream processes (such as the upcoming master initialization thread, init) inherit this namespace by default. Finally, the routine binds the root directories of the executing bootstrap process, forcing both the root pointer (fs->root) and the current working directory pointer (fs->pwd) of the active kernel initialization thread to target the root directory entry of this newly minted memory-resident root filesystem.

Only after this milestone concludes does the kernel acquire a functional concept of system pathways, empowering the VFS layer to start parsing and resolving the absolute path separator string: " / ".

Within the Linux kernel bootstrap workflow, the routine bdev_cache_init() is executed immediately succeeding mnt_init(), serving as a critical initialization step for the low-level block device management layer. Its primary technical responsibility is to call kmem_cache_create() to construct a dedicated lookaside allocation pool within the slab layer named "bdev_cache" to service struct block_device nodes, invoke register_filesystem() to register the pseudo-filesystem bdev_fs, dispatch kern_mount() to mount this hidden block device filesystem internally, and securely archive the resulting filesystem superblock (super block) memory address pointer.

Every individual disk partition, Logical Volume Manager (LVM) slice, or virtual loopback device (loop device) active across the machine is modeled inside the kernel via a discrete block_device structure instance. By establishing a dedicated lookaside cache pool for these structures, the block layer can dynamic allocate and recycle tracking nodes with peak performance efficiency.

In accordance with Linux's standard architectural doctrine that everything is a file, every standalone block device must be mapped to a valid virtual filesystem index node (inode) before the kernel can orchestrate its operations under a unified management scheme. By mounting this hidden internal bdev file system, whenever an application thread opens a device node file inside the devtmpfs tree (such as accessing /dev/sda), the kernel allocates a backing index node straight from this hidden filesystem and binds it directly to the matching block_device descriptor structure.

Across the Linux virtual filesystem layer and traditional disk-backed filesystems (such as ext4 or XFS), the Superblock acts as the definitive command center and master directory for the entire filesystem. It serves as the core data structure engineered to archive the comprehensive tracking metadata and global configuration parameters governing that explicit filesystem layout. Within the kernel source tracks, the VFS-layer superblock is structured via the descriptor struct super_block. It encapsulates highly critical tracking metrics, encompassing the physical disk block size layout, the aggregate count of disk blocks alongside total file inode allocation slots, the real-time tracking metrics logging available free disk blocks and vacant unallocated inodes, and structural filesystem status indicators (such as the Clean/Dirty validation mark used to audit whether the filesystem underwent a clean unmount pass). It concurrently stores the file system magic number (Magic Number) used to verify the precise formatting type of the partition, the volume label string, the unique disk UUID (Universally Unique Identifier), the structural mount attribute bitmasks (e.g., flagging whether the partition is locked as a read-only node versus an asynchronous read-write volume), and a master operations function pointer targeting a struct super_operations table (s_op). The super_operations method table encloses the explicit platform function handlers unique to that filesystem, mapping out the low-level logic loops required to allocate an inode, write back dirty superblock sectors onto physical disk plattters, or recycle dropped memory structures.

The primary architectural role of the superblock is to facilitate high-speed index node resolution. Whenever the memory management subsystem determines that dirty page cache footprints must be flushed and written back onto physical disk platters, the block layer is required to systematically audit all active block devices. Equipped with this global superblock memory pointer, the kernel can instantly isolate and traverse every single index node (representing every configured block device) registered under that filesystem's jurisdiction, seamlessly triggering the asynchronous background data write-back pipelines.

The final operational milestone orchestrated by the vfs_caches_init() routine is to initialize the tracking map architectures for character devices. Because Linux concurrently coordinates both block-level storage media and stream-oriented character peripherals, it calls chrdev_init() to bootstrap the foundational character device core mapping structure, cdev_map. This routine dispatches kobj_map_init() to construct the global lookup framework bridging system device numbers (composed of major and minor numbers) to their corresponding character device objects (struct cdev). This infrastructure ensures that the moment the VFS layer opens a character device node, it can leverage the hardware coordinate identifier stored inside inode->i_rdev to resolve the matching driver's method operations table (struct file_operations).

Character devices typically process data payload streams via sequential, byte-granular tracking loops, remaining entirely independent of lookaside page caching mechanisms; consequently, they do not require a complex, heavy pseudo-filesystem infrastructure to govern their lifecycles. They demand merely a streamlined, lightweight cdev_map routing matrix to instruct the core kernel precisely which device driver callback function to dispatch whenever an application interfaces with a node like /dev/tty. This mapping array is implemented as a global hash table functioning analogously to a centralized directory exchange: the compiled device number (fusing the absolute Major device number with the localized Minor device number) behaves as the search lookup key, while the address referencing the target character device descriptor structure (struct cdev) serves as the hash value.
