DETAILED ANALYSIS OF THE LINUX OPERATING SYSTEM

30.5 Peripheral and Subsystem Initialization

The routine do_initcalls() executes every single compiled initialization task bounded between the linker symbols __initcall0_start and __initcall_end. This massive execution sweep orchestrates core subsystem configurations, architecture-dependent hardware setups, peripheral module probing, device driver processing loops, and filesystem instantiation passes. The function is hosted within the central kernel initialization tree file git/init/main.c, and its definition is implemented as follows:

static void __init do_initcalls(void)
{
	int level;
	size_t len = strlen(saved_command_line) + 1;
	char *command_line;
	command_line = kzalloc(len, GFP_KERNEL);
	if (!command_line)
		panic("%s: Failed to allocate %zu bytes\n", __func__, len);
	for (level = 0; level < ARRAY_SIZE(initcall_levels) - 1; level++) {
		strcpy(command_line, saved_command_line);
		do_initcall_level(level, command_line);
	}
	kfree(command_line);
}

Commencing seamlessly from Level 0, this function loops to dispatch do_initcall_level(), systematically processing the initialization handlers bundled within each respective level's memory segment. Immediately preceding the execution of each target level, the routine copies the system's pristine command-line parameters archived inside saved_command_line over to a temporary buffer workspace, command_line.

Extensive kernel subsystems and peripheral hardware drivers authorize dynamic adjustments via these boot parameters. During the execution of do_initcall_level(), the parsing core sweeps the command line to isolate and apply the arguments corresponding to the modules compiled within the active priority level. Low-level argument parsing functions (such as parse_args) execute destructive string mutations directly inside the passed text buffer—routinely overriding whitespace characters or delimiters with a null terminator (\0) to tokenize the key-value options. Because the source buffer undergoes destructive modification during each parsing run, the routine must invoke strcpy() to completely re-overwrite the workspace with the original saved_command_line payload before entering the subsequent priority level, mathematically proving that drivers executing across later stages receive an uncorrupted, intact set of boot options.

The companion handler do_initcall_level() is alternative hosted within git/init/main.c, and its definition is implemented as follows:

static void __init do_initcall_level(int level, char *command_line)
{
	initcall_entry_t *fn;
	parse_args(initcall_level_names[level],  command_line, __start___param,
	   __stop___param - __start___param,  level, level, NULL, ignore_unknown_bootoption);
	trace_initcall_level(initcall_level_names[level]);
	for (fn = initcall_levels[level]; fn < initcall_levels[level+1]; fn++)
		do_one_initcall(initcall_from_entry(fn));
}

Prior to running the initialization handlers within a given tier, the function dispatches parse_args() to execute targeted, level-specific parameter decoding. Within this parsing interface, the array cell initcall_level_names[level] supplies the literal string text name identifying the active priority level (the operation or subsystem class name), facilitating diagnostic tracking to clarify precisely which module context is evaluating the parameters. This name matrix is defined as follows:

static const char *initcall_level_names[] __initdata = {
	"pure",
	"core",
	"postcore",
	"arch",
	"subsys",
	"fs",
	"device",
	"late",
};

The command_line buffer argument holds the raw, unparsed boot option text string (such as console=ttyS0 quiet). The parsing core tokenizes this string in place, swapping space characters or equality operators with null bytes (\0) to isolate the discrete configuration pairs.

The external tracking symbols __start___param and __stop___param are generated automatically by the linker toolchain during binary compilation. They define the absolute microarchitectural boundaries bounding the memory section within the kernel image dedicated to storing the system's parameter descriptors. Within the kernel source tree, whenever a developer registers a configuration parameter utilizing macros like module_param(), core_param(), or early_param(), the compiler leverages the compilation attribute __attribute__((section("__param"))) to force-pack the compiled parameter metadata straight into this specialized segment.

The mathematical calculation __stop___param - __start___param derives the total aggregate element count packed inside this parameter array. The level parameter provides granular filtering during the decoding sweep, restricting parse_args() to process exclusively the parameter subsets explicitly registered to match the active level index. This boundary check guarantees that throughout a specific initialization window, only the configuration arguments relevant to that exact phase undergo execution. The argument ignore_unknown_bootoption serves as a registered callback handler; as its nomenclature indicates, it instructs parse_args() to bypass and ignore unknown or non-matching boot options.

By invoking parse_args(), the do_initcall_level() routine isolates and activates exclusively the internal kernel parameters associated with the active priority tier (the parameters instantiated via module_param or __setup macros). Passing down the refreshed command_line ensures that the configuration overrides requested by the administrator during system boot (such as setting up the serial terminal via console=ttyS0) are safely bound to their target subsystems right before those subsystems activate.

Driven by a standard for loop, do_initcall_level() walks the compiled function pointer array starting from the baseline memory address of the current level up to the boundary symbol of the subsequent tier, ensuring that every single initialization callback compiled within that explicit level undergoes sequential evaluation.

The control grid initcall_levels[level] represents a static pointer matrix where each array slot references a specific physical memory coordinate situated between the master symbols __initcall_start and __initcall_end. Each cell identifies the absolute address of the primary initialization handler anchoring that respective level. This array configuration is alternative defined within the core source tracks of git/init/main.c as follows:

static initcall_entry_t *initcall_levels[] __initdata = {
	__initcall0_start,
	__initcall1_start,
	__initcall2_start,
	__initcall3_start,
	__initcall4_start,
	__initcall5_start,
	__initcall6_start,
	__initcall7_start,
	__initcall_end,
};

The do_one_initcall() function nested inside the looping structure formally triggers the execution of each target initialization function. This is the definitive location where initialization occurs, driving the kernel to branch execution directly over to the routine referenced by the fn callback tracker.

By integrating trace_initcall_level(), the do_initcall_level() routine empowers internal kernel debugging frameworks (such as ftrace or user-space utilities like bootgraph.pl) to seamlessly capture and record the exact start and completion timestamps of each priority level, generating intuitive system boot timeline graphics.

Having examined how the engine loops through each priority level, the analysis below details how an individual initialization function is processed internally by breaking down the microarchitectural behavior of do_one_initcall().

The function do_one_initcall() is hosted within the central kernel initialization tree file git/init/main.c, and its definition is implemented as follows:

int __init_or_module do_one_initcall(initcall_t fn)
{
	int count = preempt_count();
	char msgbuf[64];
	int ret;
	if (initcall_blacklisted(fn))
		return -EPERM;
	do_trace_initcall_start(fn);
	ret = fn();
	do_trace_initcall_finish(fn, ret);
	msgbuf[0] = 0;
	if (preempt_count() != count) {
		sprintf(msgbuf, "preemption imbalance ");
		preempt_count_set(count);
	}
	if (irqs_disabled()) {
		strlcat(msgbuf, "disabled interrupts ", sizeof(msgbuf));
		local_irq_enable();
	}
	WARN(msgbuf[0], "initcall %pS returned with %s\n", fn, msgbuf);
	add_latent_entropy();
	return ret;
}

Immediately preceding execution, the function cross-checks whether the target initialization callback has been explicitly disabled by the administrator via the initcall_blacklist= boot parameter. This check is incredibly useful during debugging passes to bypass and isolate misbehaving or corrupted hardware drivers that would otherwise trigger a fatal crash during boot. If the function is not blacklisted, the engine activates the initcall trace trackers, dispatches the handler callback to execute the hardware initialization, and subsequently stops the trace trackers, capturing the precise temporal duration consumed by that explicit module setup routine.

The kernel records the absolute preemption count value via preempt_count() before executing the callback. If the routine alters the preemption balance upon winding down—for instance, if a driver developer invokes a preempt_disable() tracking primitive but completely omits the matching preempt_enable() cleanup call—the kernel forcefully overrides the corruption to reset the count back to its original value and raises an explicit error. Without this defensive override, the operating system could enter a state where task preemption is permanently blocked, freezing the scheduling core and locking up the machine [17.3].

Similarly, if an errant initialization function disables local CPU interrupts and terminates without re-enabling them, the kernel aggressively executes a recovery path via local_irq_enable() to reopen the interrupt channels and logs a critical system warning [24.2]. Allowing local interrupts to remain blocked would permanently blind the CPU core to physical timer event crystals and peripheral device exceptions, causing the system to lock up.

Upon the conclusion of each individual initialization function, the engine dispatches add_latent_entropy(). This call evaluates the slight microsecond-scale timing variances and scheduling states resulting from that function's execution path to inject fresh non-deterministic data blocks straight into the system's primary input pool, continuously strengthening the unpredictability of the random number generator [22.3].

The do_basic_setup() framework serves as the definitive microarchitectural boundary separating the phase where the kernel initializes its own internal subsystems from the phase where it initializes external peripheral hardware devices. Upon its clean termination, the kernel stands fully prepared to search out the physical storage disk to launch the primary user-space initialization executable at /sbin/init, hand-shaking control over to user space [26.6, 28.1, 30.2].

Following the execution of this massive initcall priority sequencing grid, kernel_init_freeable() dispatches kunit_run_all_tests() to process the comprehensive suite of internal kernel testing code. The KUnit architecture is a lightweight, unit-testing framework built natively inside the Linux kernel space. Heavily inspired by user-space paradigms like JUnit, Python's unittest, and GoogleTest, this testing core empowers kernel developers to compile and execute white-box validation routines directly inside the kernel context, targeting core functions managing virtual filesystems, peripheral device drivers, or memory structures.

Because these validation modules execute natively as a component of the privileged kernel image, they retain full structural access to internal, non-exported helper routines and hidden symbols that are alternative locked down and shielded from standard dynamic kernel modules (functions not exported via the EXPORT_SYMBOL macro family). By pairing the framework with the kunit_tool utility and User-Mode Linux (UML), developers can compile the entire operating system image down into a standard user-space executable, running dozens of white-box tests on a host development machine within a few split-seconds. KUnit tests can be configured to run automatically as built-in routines during the system boot sequence, or compiled as modular units that trigger their test passes the moment the driver module is dynamically inserted into the running kernel. The finalized test results are formatted and exported using the standardized KTAP (Kernel Test Anything Protocol) syntax, making the output exceptionally easy to parse via automated user-space diagnostic scripts or continuous integration (CI) automation pipelines.

This unit testing architecture organizes its validation passes by leveraging three primary data structures: the test suite container (struct kunit_suite), the test case descriptor (struct kunit_case), and the active test runtime context tracker (struct kunit). The test suite represents the primary organizational block within the KUnit framework, bundling together a cluster of related testing vectors that share common setup traits or target an identical subsystem. It orchestrates their collective execution and maps out the shared pre-test initialization callbacks alongside post-test cleanup handlers. The test case structure defines an individual validation function alongside its unique text name identifier, providing the structural canvas where developers write their explicit verification loops. The test context tracking object manages real-time metadata archiving the active status of the running test; it is driven entirely by the KUnit core engine, providing developers with a valid context to provision private tracking data or execute defensive validation checks. The following implementation snippet demonstrates how to compile and register a custom test suite using KUnit macros, where my_test_case_1() serves as the concrete validation target:

/* 1. Define the concrete unit test case function */
static void my_test_case_1(struct kunit *test) {
    KUNIT_EXPECT_EQ(test, 1 + 1, 2); 		// Assertion helper macro verifying that 1 + 1 equals 2
}
/* 2. Assemble the test cases into a structural array */
static struct kunit_case my_test_cases[] = {
    KUNIT_CASE(my_test_case_1),		// Maps .run_case = my_test_case_1 and .name = "my_test_case_1"
    {} 							// The tracking array must terminate with an empty structure stub
};
/* 3. Define the parent test suite container */
static struct kunit_suite my_test_suite = {
    .name = "my_subsystem_test_suite",
    .test_cases = my_test_cases,
};
/* 4. Register the completed suite with the KUnit core */
kunit_test_suite(my_test_suite);

The routine kunit_run_all_tests() operates as the central initialization and dispatch hub for the kernel's unit testing framework during boot. It first dispatches kunit_print_tap_header() to stream out standard Test Anything Protocol (TAP) header blocks onto the log infrastructure. This standardized formatting ensures that external automation scripts can seamlessly decode the incoming diagnostic results piped across the system's serial console [24.1].

Following this header transmission, kunit_run_all_tests() executes a systematic traversal across the compiled test suite structures bounded globally between the compiler symbols __kunit_suites_start and __kunit_suites_end. Inside this traversal loop, it passes each discovered suite descriptor down to the internal handler __kunit_test_suites_init() to process its testing vectors. The concrete testing sequence executed during this pass includes:

  • Suite Initialization via kunit_init_suite():
    Initializes runtime assets and sets execution status flags for the target test suite. This phase constructs a dedicated debugfs interaction gateway, carving out an independent directory named after the test suite under the tracking path /sys/kernel/debug/kunit/. Through these virtual files, automated testing systems or human operators can directly inspect test outcomes or programmatically trigger a rerun of the test suite while the system remains live.

  • Executing the Validation Suite via kunit_run_tests():
    Formally dispatches all compiled test cases packed within the suite and records their completion metrics. The core operational steps processed within this execution block encompass:

    • Emitting the Subtest Header: Calls kunit_print_subtest_start() to stream compliant KTAP protocol header logs out to the system console or the main dmesg buffer, documenting the unique name of the test suite alongside the total volume of test cases scheduled for execution.

    • Traversing the Test Matrix: Deploys the loop macro helper kunit_suite_for_each_test_case() to systematically walk every individual test case contained within the suite. Inside this loop, the helper function kunit_run_case_catch_errors() sequentially triggers the test suite's private setup function (.init), the core test case validation routine (.run_case), and the suite's cleanup function (.exit). Crucially, rather than executing the test callback directly along the naked stack, the framework encapsulates the invocation within an exception-catching abstraction sandbox to cleanly handle unhandled errors or kernel faults without destabilizing the broader bootstrap process.

  • Emitting Suite Summaries:
    Outputs a consolidated results block detailing the terminal status (PASSED or FAILED) of the entire suite.

During the compilation and linking phase, every test suite pointer instantiated via the kunit_test_suite() macro family is collected by the toolchain and packed continuously into a dedicated ELF memory segment bounded globally by the symbols __kunit_suites_start and __kunit_suites_end.

Upon the successful conclusion of the KUnit white-box testing pass, the routine kernel_init_freeable() dispatches console_on_rootfs() to allocate and wire standard input, standard output, and standard error file handles (stdin, stdout, stderr) for Process 1 (PID 1, the upcoming init thread context). The technical operations executed by console_on_rootfs() encompass:

  • Opening the Master Console via filp_open("/dev/console", O_RDWR, 0): Establishes an open session targeting the physical system console character device node. This path acts as a virtual device layer that the VFS core automatically routes to point to the definitive physical terminal hardware interface (such as a serial UART port or a graphics display device) resolved from the console= boot parameters [24.1, 27.6].

  • Defensive Error Auditing: If the file opening operation encounters a failure condition, it indicates that the kernel is completely blind to a valid interactive terminal device, prompting the system to emit a warning log. This anomaly traditionally signals that the rootfs image is missing the mandatory low-level device nodes under its /dev path, or the physical hardware device driver failed to load during the preceding stages.

  • Multiplexing the File Object via init_dup(): The routine dispatches the file descriptor duplication helper init_dup() three times consecutively to replicate and reference the single unique struct file instance originally instantiated in memory by filp_open(). The first duplication pass claims File Descriptor 0 to back standard input (stdin), the secondary pass claims File Descriptor 1 to back standard output (stdout), and the final pass claims File Descriptor 2 to drive standard error (stderr). Consequently, this singular /dev/console file object tracks concurrently across three distinct functional file descriptors within the task's lookup array, remaining active throughout the entire operational lifecycle of the kernel image [27.6].

Because every downstream user-space process thread in Linux scales as a direct historical descendant of PID 1, every newly spawned user application automatically inherits these three pre-configured file descriptors by default:

  • 0: Routes the thread to process incoming user input streams harvested from /dev/console (stdin).

  • 1: Routes the thread to pump standard text output payloads straight to /dev/console (stdout).

  • 2: Routes the thread to dump error logging and diagnostics payloads straight to /dev/console (stderr).

At this explicit junction along the system bootstrap timeline, the core initialization tasks are fundamentally finalized. Moving forward, kernel_init_freeable() dispatches init_eaccess() to audit whether the file path compiled within the global string variable ramdisk_execute_command physically resides within memory, confirming whether the system incorporates an early user-space ramdisk (initramfs/initrd) setup script.

The variable ramdisk_execute_command represents a global kernel string tracking pointer that archives the exact file path of the absolute first user-space binary application to be launched the moment the kernel mounts the initial RAM disk. Once the operating system completes its baseline subsystem configurations and finishes extracting the compressed ramdisk image into the temporary rootfs boundary, it must hand off execution control to an unprivileged task context to orchestrate late-stage device configurations (such as inserting custom driver modules or mounting the definitive primary physical storage partition) [25.2]. This variable preserves that targeted program path, defaulting standard to evaluate as "/init", though it can be dynamically overridden by the administrator at boot time via the rdinit= command-line flag. For example, passing the command-line override rdinit=/bin/sh instructs the kernel's execution core to bypass the standard initialization scripts to drop control straight into a bare-metal interactive shell prompt.

If the file path referenced by ramdisk_execute_command validates as present in the ramdisk memory tree, the kernel invokes run_init_process() to launch the application. If this preliminary process triggers an execution fault or the target file node is absent from the file layout, the initialization engine falls back to attempt launching the program path specified via the alternative init= boot flag, or systematically sweeps standard path locations including /sbin/init and /etc/init.

Within the Linux architecture, the /init script file (housed inside the compiled initramfs archive that was pushed into physical RAM by the bootloader during early boot) functions as the definitive heart of the initial memory-resident filesystem [25.2]. It represents the absolute first user-space application thread (PID 1) allowed to execute on the machine following the mounting of the ramdisk. Typically structured as an automated shell script, the execution of /init coordinates the following system operations:

  • Mounts the foundational virtual and pseudo-filesystems—including populating the /proc, /sys, and /dev directory paths—to open the primary kernel communication channels [27.6, 28.1, 28.4].

  • Performs automated hardware probing sweeps to discover and load the concrete storage controller drivers (such as SATA, NVMe, or hardware RAID modules) or network adapter drivers. Stripped of this automated module injection, the core kernel would remain completely blind to the physical hard drive hardware.

  • Parses the kernel command-line arguments to resolve the explicit root=UUID=... string block, locating the definitive primary storage disk partition.

  • If the target primary hard drive partition incorporates physical disk encryption, the script manages user interaction to prompt for the decryption passphrases and energizes the device mapper loops to unlock the data block.

  • The moment the true primary hard drive partition is successfully resolved and mounted, the script dispatches a root-swapping routine to pivot the system root over to the physical hard drive, permanently hand-shaking PID 1 execution control over to the storage disk's standard /sbin/init daemon.

If the file target pointed to by ramdisk_execute_command validates as absent from memory, the routine clears the tracking string pointer entirely and dispatches the core function prepare_namespace() to prepare and mount the permanent physical root filesystem (rootfs). This milestone marks the definitive moment where the kernel completes its comprehensive self-testing sweeps to branch execution over to a production user-space initialization framework (such as a standard binary init or the enterprise systemd daemon) [30.2].

The function prepare_namespace() acts as the definitive command center for the kernel's storage partition validation and root directory mounting pipelines. Its internal execution paths process the following milestones:

  • Handling Intentional Storage Boot Delays: If the kernel command-line arguments specify a root_delay parameter, the initialization sequence logs a trace and drops the execution path into a synchronous sleep phase (ssleep). This delay is critical on server or embedded platforms to afford slow, asynchronous, or external storage peripherals (such as USB drives, external SAS enclosures, or FireWire block arrays) acceptable time to complete their low-level hardware enumeration loops before the kernel attempts a partition query.

  • Awaiting Device Discovery Stabilization: Dispatches wait_for_device_probe() to block the thread until the driver framework registers that all asynchronous background hardware probing passes have safely finished. This ensures that the kernel has comprehensively attempted to load, bind, and stabilize the drivers for all discovered physical host controllers [29.4].

  • Assembling Software RAID Ensembles: Invokes md_run_setup() to process software-defined RAID properties. If the designated boot partition resides inside a Linux Software RAID configuration (such as booting off a /dev/md0 multi-disk target), this routine aggregates the physical disk metadata and assembles the array to bring the logical block device online.

  • Resolving and Parsing the Target Root Device: Inspects the global tracking array saved_root_name to process the storage parameter requested via the root= boot flag.

    • Flash Media Bypass Path: If the character string identifies that the target is a raw flash memory abstraction layer common in embedded designs (such as matching an MTD or UBI flash layout string like "mtd" or "ubi"), the filesystem core recognizes that the root is not a conventional spinning platter or block partition. It skips standard disk enumeration loops to mount the target directly via mount_block_root() and branches control straight to the trailing cleanup sequence (goto out).

    • Converting Alphanumeric Names to Canonical Device Keys: For standard block partitions (such as a SCSI or NVMe drive path like /dev/sda1), the routine dispatches name_to_dev_t() to parse the string token and translate it into a structured, internal kernel-space device integer configuration identifier (ROOT_DEV). It subsequently increments the text string memory pointer forward by 5 bytes to discard the leading literal characters "/dev/" from the descriptor name.

  • Executing Legacy Initrd Loading Loops: Fires the sub-routine initrd_load() to check for an integrated RAM disk layout. If this loading pass returns a successful validation status, the routine shifts execution control straight to the concluding stage via a jump to the label out.

  • Enforcing Persistent Storage Queries under rootwait Constraints: If the calculated root device tracking key evaluates as vacant (ROOT_DEV == 0) and the administrator explicitly enabled the rootwait option on the command line, the kernel drops into a synchronous while loop, checking driver_probe_done() and retrying name_to_dev_t() every 5 milliseconds. This blocking watch loop stops the system from prematurely declaring a boot failure when running on contemporary storage pipelines that exhibit variable hardware discovery timelines (such as high-speed NVMe nodes or external USB 3.0 lines that stabilize later than the core boot sequence). Upon breaking out of the watch loop, the subsystem dispatches async_synchronize_full() to ensure all out-of-order storage tracing threads have safely finalized their operations.

  • Mounting the Primary Storage Platter: Invokes the core routine mount_root() to physically mount the primary block device partition resolved from the root= string directly onto the current execution path context, constructing the definitive new root repository window.

  • Binding the Device Nodes Filesystem: Calls devtmpfs_mount() to mount the automated device nodes filesystem onto the designated /dev path exposed within the freshly attached physical primary storage partition, ensuring user-space tasks maintain instant, un-shared access to interact with low-level peripheral drivers [27.6, 30.2.1].

  • Pivoting the Global Mount Tree Hierarchy: Dispatches the VFS core mounting primitive init_mount(".", "/", NULL, MS_MOVE, NULL). This operation uses the current context directory symbol "."—which anchors the memory address coordinates of the physical storage partition mounted by mount_root()—and shifts that entire compiled mount tree structure to override the temporary boot root, cementing it as the absolute master "/" root of the virtual filesystem architecture.

  • Executing the Ultimate Namespace Chroot Migration: Invokes init_chroot(".") to forcefully pivot the executing process thread's root directory coordinates to match this newly established root junction. This operation successfully terminates the kernel's dependency on the temporary ramdisk layout, guiding the primary execution context permanently into the "User World."

In summary, the conditional block structured as if (init_eaccess(..)) operates as a definitive tracking mechanism engineered to verify whether the memory-resident boot-stage startup scripts are present and functional. If the check flags that the ramdisk script environment is absent or unconfigured, the kernel changes tracks to mount the physical hard drive partitions.

Finally, upon wrapping up the storage mounting loops, kernel_init_freeable() dispatches a call to integrity_load_keys() to load the security public keys and cryptographic certificates consumed by the Integrity Measurement Architecture (IMA) and the Extended Verification Module (EVM).

  • IMA Validation Subsystem: Assumes sole responsibility for verifying the absolute integrity of execution binaries, shared objects, and library files prior to authorizing their execution or opening their handles (validating the blocks against strict cryptographic signatures or SHA hashes). integrity_load_keys() extracts the pre-populated trusted certificate keys compiled into the secure kernel data structures and writes them onto the system's global keyrings [27.3]. This provides the verification engine with the public keys required to verify that subsequently launched user-space binaries or dynamic link libraries have not suffered malicious runtime manipulation or code injection.

  • EVM Hardening Subsystem: Safeguards the extended security attributes (xattrs) associated with filesystem nodes, locking down attributes including file access permission bitmasks, ownership user mappings, and the embedded IMA signature envelopes themselves. This protection grid ensures that an attacker cannot alter a file's metadata descriptors (such as attempting an privilege escalation exploit by transforming a read-only configuration script into a world-writable node) to step around the kernel's MAC enforcement checks [27.4].

Upon the clean conclusion of the kernel_init_freeable() block, the system's core initialization sweeps are essentially finalized. Every memory page frame explicitly decorated with the compilation attribute __init (the data blocks bounded precisely between the tracking markers __init_begin and __init_end) becomes obsolete, and the main system thread kernel_init() prepares to process sequential memory reclamation sweeps to free these pages back to the allocator.
