DETAILED ANALYSIS OF THE LINUX OPERATING SYSTEM

25.4 Initializing the NUMA Policy Framework

Within the Linux kernel, the NUMA policy (Memory Policy) dictates which explicit physical slot (Socket/Node) and memory bank the kernel should prioritize whenever an executing program requests memory. Across multi-socket server platforms (such as dual-socket Intel Xeon or AMD EPYC installations), executing a memory access transaction targeting a localized memory node (memory connected directly to the active CPU socket) is substantially faster than accessing a remote memory node (which requires traversing the interconnect fabric bus to talk to memory wired to an alternate socket). The NUMA policy framework is engineered specifically to manage and optimize under these microarchitectural latency discrepancies.

The core kernel exposes four primary operational memory allocation policies, which can be configured from user space via the numactl utility tool or programmatically requested via the set_mempolicy() system call:

  • MPOL_DEFAULT (The Default Modality): Instructs the allocator to attempt to fulfill memory allocation requests preferentially from the localized memory node hosting the CPU core that is currently executing the calling thread. This constitutes the optimal configuration choice for the vast majority of general-purpose applications, yielding the lowest absolute access latency.

  • MPOL_BIND (Enforced Binding): Enforces a strict restriction dictating that physical memory blocks can be shunted exclusively from a predefined, specific subset of memory nodes. If these targeted nodes experience full resource exhaustion, subsequent allocation passes will fail immediately and raise an Out-of-Memory (OOM) fault. This modality is highly optimized to run high-performance database engines (such as Redis or MySQL), guaranteeing that data blocks never migrate or hop across cross-node interconnect boundaries.

  • MPOL_INTERLEAVE (Interleaved Modality): Uniformly distributes and scatters physical page frames across all designated nodes in a round-robin cycle (such as placing Page 0 on Node A, Page 1 on Node B, and so forth). This layout is useful for processing massive computational tasks that demand extensive memory bandwidth metrics (such as wide-scale scientific simulation computations), maximizing aggregate throughput by driving the physical memory controllers of all nodes in parallel.

  • MPOL_PREFERRED (Preferred Modality): Directs the engine to exhaustively attempt memory page acquisition from a targeted node, but authorizes an automatic fallback path to harvest space from alternative nodes if the preferred pool runs low. This represents the ideal configuration choice for deployment scenarios that strive to preserve cache and memory locality advantages but cannot tolerate process crashes due to localized capacity shortages.

The structural tracking of NUMA policies is managed across three distinct logical tiers: system-level, task-level, and memory-region-level. The system-level boundary is established via the routine numa_policy_init(), which defaults to enforcing a local-first allocation hierarchy. The task-level hierarchy (Task Policy) defines the baseline inheritance constraint that a specific process, execution thread, or its subsequent downstream child threads must conform to. Finally, the memory-region-level hierarchy (VMA Policy) implements isolated, independent allocation constraints targeted directly at a specific, designated virtual address range mapped inside the program's address space.

If these memory allocation properties are configured or balanced improperly at runtime, the platform can fall victim to the notorious NUMA Node Imbalance Exception. Under this anomalous performance condition, the physical capacity of Node 0 faces near-total saturation, forcing the kernel to initiate high-frequency background page swapping passes (Swap), while Node 1 concurrently retains a massive repository of unallocated free memory blocks.

The routine numa_policy_init() represents a critical structural step within the Linux kernel initialization sequence, assuming sole responsibility for assembling the Non-Uniform Memory Access (NUMA) memory policy tracking framework during early system boot. Its primary technical milestone is to establish the system-wide global baseline default policy, which it satisfies by binding the master system configuration to adopt the MPOL_DEFAULT attribute. For the overwhelming majority of standard production deployments, this configuration ensures the execution of strict Local Allocation behavior—forcing each individual CPU core to channel its physical page requests preferentially toward its own physically attached memory banks (the Local Node) to secure the lowest achievable hardware access latency. This function is hosted within the memory management source file git/mm/mempolicy.c, and its definition is implemented as follows:

void __init numa_policy_init(void)
{
	nodemask_t interleave_nodes;
	unsigned long largest = 0;
	int nid, prefer = 0;
	policy_cache = kmem_cache_create("numa_policy",
				 sizeof(struct mempolicy), 0, SLAB_PANIC, NULL);
	sn_cache = kmem_cache_create("shared_policy_node",
			     sizeof(struct sp_node), 0, SLAB_PANIC, NULL);
	for_each_node(nid) {
		preferred_node_policy[nid] = (struct mempolicy) {
			.refcnt = ATOMIC_INIT(1),
			.mode = MPOL_PREFERRED,
			.flags = MPOL_F_MOF | MPOL_F_MORON,
			.v = { .preferred_node = nid, },
		};
	}

	nodes_clear(interleave_nodes);
	for_each_node_state(nid, N_MEMORY) {
		unsigned long total_pages = node_present_pages(nid);
		if (largest < total_pages) {
			largest = total_pages;
			prefer = nid;
		}
		if ((total_pages << PAGE_SHIFT) >= (16 << 20))
			node_set(nid, interleave_nodes);
	}
	if (unlikely(nodes_empty(interleave_nodes)))
		node_set(prefer, interleave_nodes);
	if (do_set_mempolicy(MPOL_INTERLEAVE, 0, &interleave_nodes))
		pr_err("%s: interleaving failed\n", __func__);
	check_numabalancing_enable();
}

This routine illustrates how the Linux kernel initializes its early NUMA tracking profiles, deploying an absolute execution logic that diverges from standard user-space task setups. Throughout the early system bootstrap sequence, the kernel deliberately chooses the MPOL_INTERLEAVE (interleaved) memory allocation modality as its temporary initial strategy rather than defaulting straight to local node allocation [July 12, 2026].

The function first dispatches kmem_cache_create() to instantiate two specialized lookup pools within the slab allocator, named "numa_policy" (referenced via the lookaside cache pointer policy_cache) and "shared_policy_node" (referenced via the lookaside cache pointer sn_cache). These pools are reserved to house struct mempolicy descriptors and struct sp_node descriptors, respectively. The sp_node structural container is leveraged exclusively to manage and track NUMA memory allocation constraints applied over shared memory segments (shm). If a severe low-memory constraint thwarts the creation of these critical lookaside caches during early boot, the kernel triggers an instant fatal exception via SLAB_PANIC, crashing the system.

Following this allocator setup, the routine loops through each independent NUMA node via for_each_node() to prepare a localized preferred memory policy (MPOL_PREFERRED), programmatically binding each node to treat itself as its own preferred destination allocation target. This configuration ensures that the moment the kernel transitions into its standardized operational modes, the core buddy allocator can seamlessly honor physical proximity rules to secure minimal data transfer delays. However, while these localized self-preferred tracking templates are pre-populated in memory, the subsequent execution code immediately invokes do_set_mempolicy() to forcefully configure the active kernel bootstrap thread to run under the interleaved memory allocation mode.

The underlying engineering objective during early system bootstrap is to scatter and distribute critical boot-stage datasets uniformly across the SoC's separate hardware sockets and memory controllers. To satisfy this requirement, the function iterates systematically through all active memory-populated slots across the platform (nodes exhibiting the N_MEMORY node state), and evaluates each node's physical capacity; any memory node whose footprint satisfies the condition ≥ 16 MiB (derived via total_pages << PAGE_SHIFT) is automatically appended onto the interleave_nodes destination bitmask tracking array. If every discovered hardware node falls beneath this 16 MiB threshold barrier, the routine isolates the single largest node across the platform and appends its index to serve as the default fallback target inside the mask.

At this juncture, the kernel executes do_set_mempolicy(MPOL_INTERLEAVE, ...) to bind this compiled interleaved bitmask onto the initialization thread context (Process 0). This strategic configuration path effectively forces early core allocations—including massive kernel tracking structures, memory cache lists, system page tables, and early device driver parameters—to be distributed across the disparate NUMA sockets, preventing these large-scale early datasets from entirely saturating Node 0 and balancing execution load across the available memory controller arrays.

At the very conclusion of the routine, the kernel dispatches a call to check_numabalancing_enable() to determine whether it should activate the Auto-NUMA Balancing engine. When this runtime feature is active, a background kernel tracking thread continuously monitors cross-node access patterns and dynamically migrates physical page frames across sockets to bring data blocks closer to the CPU cores that actively parse them.

This function guarantees that the kernel avoids choking the primary memory node during early boot sweeps. Because process attributes and memory configuration bitmasks are natively inherited by child execution blocks during replication cycles, all subsequently spawned user-space processes (including the upcoming definitive master initialization thread, init / PID 1) will default to inheriting this interleaved NUMA configuration unless explicitly altered. Once the operating system successfully transitions to execute user-space code paths, applications can smoothly modify their localized tracking constraints back to favor the standard MPOL_DEFAULT low-latency profile by issuing a native set_mempolicy() system call.
