DETAILED ANALYSIS OF THE LINUX OPERATING SYSTEM

15.4 Page Swapping and Virtual Memory Mapping

Within the Linux system, each process possesses its own unique virtual memory space, and the available virtual memory capacity within each space is completely unconstrained by the literal size of the physical memory. When the memory footprint demanded by the active processes surpasses the physical memory capacity, the operating system writes portions of the physical memory that are currently unutilized out onto an external storage device. This external storage space dedicated to temporarily preserving physical memory payloads is designated as the swap partition. To facilitate seamless file swapping operations, Linux reserves specific lookaside buffers within the virtual memory space for disk file swapping consumption.

Because Linux natively supports multi-process execution, files or library functions loaded into memory might be concurrently utilized by multiple independent processes. If these files or library functions had to be re-read from the hard disk drive upon every single invocation, it would drastically degrade program execution velocity. To circumvent this bottleneck, Linux also carves out dedicated tracking buffers utilized to preserve this shared data.

Throughout their execution lifecycles, programs generate a substantial volume of temporary runtime data. Due to the microarchitectural characteristics of computer hardware, aggregating this data together not only optimizes overall memory utilization efficiency and streamlines memory management but also enables the CPU to access data via immediate addressing or direct addressing modes rather than indirect pointing mechanisms. This effectively minimizes address arithmetic overhead and elevates program processing throughput, giving rise to the concepts of the heap and the stack. Each individual process maintains an independent heap and stack, which serve as localized buffers for tracking temporary data.

Although the lookaside buffers dedicated to disk file swapping vary slightly from the standard process heap and stack setups, these two categories of memory regions share a core characteristic: their raw physical targets cannot be interfaced with directly via unmapped virtual addresses, meaning their high-level buffer management workflows share significant commonality. Consequently, Linux adopts a unified infrastructure to manage both buffer categories, introducing variances solely within their concrete architectural mapping methodologies.

To streamline buffer orchestration, Linux categorizes virtual memory tracking structures into two primary functional types. The first type is dedicated to storing data consumed dynamically by running applications; this category of virtual memory region is designated as anonymous memory. Both the process heap and stack belong to the anonymous memory classification. The alternative memory type is dedicated to executing data swapping passes with the hard disk drive, a category designated as file-backed memory. File-backed memory zones are utilized to cache files read from or written to disks, swap partition files, shared library functions, and the binary execution code of the program itself. Figure 15-11 illustrates the explicit mapping relationships between various file types and the virtual address canvas.

Linux differentiates between anonymous memory and file-backed memory by evaluating the least significant bit (b0) of the mapping field enclosed within the physical page frame descriptor struct page. When this least significant bit (the PAGE_MAPPING_ANON bit) is set to 1, it indicates that the current page frame maps to anonymous memory; under this scenario, the mapping pointer references a specialized structural backbone named struct anon_vma (see §15.4.2). Conversely, when this least significant bit evaluates to 0, it signifies that the current page frame maps to file-backed memory, under which constraint the mapping field acts as a valid pointer referencing an address space tracking structure (struct address_space).

15.4.1 Memory Eviction and Page Release

When utilizing file-backed memory, the physical memory capacity constraints require the processes to frequently execute data swapping passes with disk storage (encompassing both regular files and swap partition files). An efficient file swapping mechanism minimizes the frequency of disk read/write cycles, thereby enhancing overall program execution throughput. Linux achieves this by managing five fixed-length Least Recently Used (LRU) lists classified into three operational categories to guide page swapping operations. These five LRU lists encompass anon_active, anon_inactive, file_active, file_inactive, and unevictable. Among them, anon_active and anon_inactive are dedicated to orchestrating page swapping for anonymous memory; file_active and file_inactive handle page swapping for file-backed memory; and the unevictable list preserves pages that are structurally prohibited from being evicted to disk storage. For instance, when Linux mounts a ramfs filesystem, the files contained within it must remain permanently resident in physical memory throughout the system runtime lifecycle.

When a process executes a memory read operation, if the targeted page frame already resides on an active list, the subsystem promotes this page to the head boundary of that active list, shunting the preceding entries downward by one slot position. If the targeted page is located on an inactive list, the system similarly promotes this page to the head boundary of the corresponding active list, while shunting the pages originally preceding it on the inactive list downward by one slot position. If a page fault exception manifests—indicating that the requested payload data is completely absent from physical memory—the operating system's page fault handler evicts and releases the page frame situated at the tail boundary of the corresponding inactive list (xx_inactive) (see §15.6) and reads the correct data block back from disk storage. Upon initially loading a page from disk, the newly fetched page frame is positioned at the head boundary of the inactive list, pushing the remaining elements on that list downward by one slot position. To maintain clarity, this overview simplifies the operational tracking loops of the LRU subsystem. In practical execution, additional metrics are factored in; for instance, when deciding whether to promote a page from an inactive list to an active list, the allocator evaluates the chronological interval between two consecutive accesses to the exact same page, thereby preventing thrashing where a single page is repeatedly evicted and re-read. These lists are similarly manipulated during large-scale page reclamation passes. Figure 15-12 illustrates several common structural state changes across the LRU lists.

The majority of LRU list structural topologies and memory eviction routines are defined within the source file git/mm/swap.c. The internal state transformation and relocation loops across these lists are executed by the function mark_page_accessed(). Readers interested in pursuing deeper architectural specifics can review the source code contained within that file.

15.4.2 Mapping Between Virtual Addresses and Caching Buffers

Both anonymous memory and file-backed memory reside within dedicated private caching buffers. The execution program is unable to interface with these buffers directly via unmapped virtual addresses; instead, it must employ a mapping layer to bind virtual addresses or file offsets to the caching buffer space, thereby ensuring the correct dataset can be retrieved. To achieve structural mappings from disk files and anonymous memory domains into the runtime caching buffers, Linux defines four core data structures. Their primary structural technical objective is to govern the process's virtual memory intervals, and to enable the system—upon encountering a page eviction or a Copy-on-Write (CoW) cycle—to rapidly perform a reverse lookup from a physical page frame back to all referencing virtual memory areas.

These primary architectural structures encompass:

  • struct mm_struct (The mm Structure):
    The memory descriptor canvas. Exactly one instance is assigned to each individual process, which encapsulates fields tracking the localized cache areas consumed by the thread context, the root node of the process's VMA red-black tree, the aggregate address space footprint, the cumulative number of virtual page frames, the precise boundary markers for the heap, stack, data, code, and uninitialized variable (bss) segments, a structural tracking pointer referencing the standalone VMA sequential linked list, environment variable segments, alongside diverse runtime statistic counters and memory watermarks. The VMA red-black tree is structurally composed of all vm_area_struct instances tied to this parent mm_struct.

  • struct vm_area_struct (The VMA Structure):
    The virtual memory area descriptor. It delineates a single physically non-contiguous but virtually continuous block of memory space assigned to a process. It primarily contains the sequential pointer hooks vm_next and vm_prev utilized to thread together the process's absolute buffer chain, the virtual address starting boundary, the virtual address ending boundary, the structural red-black tree node tracking member vm_rb used to hook the VMA instance directly onto the mm_struct parent tree, a pointer tracking back to the owner mm_struct, an rb tracking node utilized to attach the VMA container into the global interval tree address_space->i_mmap tracking backed disk files, a pointer targeting the explicit anon_vma context managing this caching zone, a list head tracking member anon_vma_chain grouping all anon_vma_chain bridge structures intersecting this VMA node, and a vm_file structural file pointer referencing the backing file descriptor (which evaluates as a null pointer when tracking anonymous memory blocks).

  • struct anon_vma (The AV Structure):
    While resolving a virtual address down to its corresponding physical address is efficiently handled via forward page table walks, the inverse sequence—mapping a raw physical address back to its referencing virtual addresses (known as reverse mapping or rmap)—represents a significant microarchitectural challenge due to the unidirectional design of page tables. A critical application context for reverse mapping manifests during memory eviction passes: the kernel must perform an rmap lookup to discover every virtual address referencing the target physical page frame, and subsequently modify those page table entries to point directly to the page's slot within the swap partition.
    The primary functional purpose of the anon_vma structure is to facilitate high-performance reverse mapping queries. It encapsulates 6 distinct fields, where the root field points to the definitive root node of the active anon_vma ancestry tree, and the parent field references the corresponding anon_vma context of the parent process that invoked the original fork() cycle. Across multi-generational process hierarchies, parent-child memory sharing paths introduce complex exclusive versus shared memory mapping boundaries. To streamline tracking, Linux arranges these process structures hierarchically into an ancestry tree, where all descendant anon_vma instances resolve their lineage back to the initial ancestral root via the root pointer.
    The degree counter field logs the total count of direct child anon_vma structures; when degree evaluates to less than 2, the current structure is eligible to serve as the immediate parent anon_vma framework for a subsequent child process layer.
    The rb_root field anchors the root node of a specialized interval red-black tree composed of anon_vma_chain bridge structures, which links all VMAs intersecting the current anon_vma instance. This specific interval tree structure aggregates all referencing VMAs across the entire system that currently map this chunk of anonymous memory (achieved structurally via the intermediary anon_vma_chain components). This binary search tree links all concurrent VMAs belonging to distinct processes (or threads) that share access to the same anonymous physical memory frames. Consequently, it encompasses not only the local process VMA but also the VMAs of all child and grandchild descendant processes generated via fork() cycles, provided these descendants continue to share this specific memory interval. If a descendant process triggers a Copy-on-Write (CoW) exception, Linux creates a fresh memory block and hooks a newly instantiated anon_vma structure onto its local red-black interval tree, thereby transitioning it to manage its own isolated anonymous memory pages.

  • struct anon_vma_chain (The AVC Structure):
    The primary architectural role of the anon_vma_chain structure is to act as a bridge establishing a clean intersection between the anon_vma context and individual VMAs, which it accomplishes by configuring its vma and anon_vma fields to point directly to their respective target structures. Furthermore, this structure serves a dual purpose as a standard list node labeled same_vma (hooked onto the list head anchored at the VMA's local anon_vma_chain field) and as an active binary tree node labeled rb (hooked into the interval red-black tree anchored at the anon_vma structure's rb_root field).
    The AVC tracking chains are woven together via the same_vma list element, and the base head of this chain is managed within the anon_vma_chain field of the corresponding VMA structure, thereby logging all distinct anon_vma contexts intersecting that specific VMA container. Concurrently, the interval red-black tree is threaded together via the rb node element, tracking all distinct VMAs that are managed under the jurisdiction of the specified anon_vma structure.
    Within the reverse mapping subsystem of the Linux memory management framework, the anon_vma and anon_vma_chain structures work in tandem to solve the core architectural problem of discovering every virtual memory area mapping a given anonymous physical page frame. The internal red-black tree managed inside the anon_vma instance preserves a comprehensive index of all VMAs that could potentially map the same physical page frames.

As illustrated in Figure 15-13, the initial vm_area_struct instance belonging to a process can be directly resolved from its parent mm_struct. Evaluating this VMA structure yields multiple parameters regarding the address space footprint currently consumed by the process. Furthermore, via the mm_struct, the system can interface with the global VMA red-black tree, allowing the kernel to rapidly look up a specific VMA instance of interest.

Figure 15-14 shows the contiguous tracking chain composed of all VMAs assigned to a process. Traversing this sequential list enables the kernel to inspect every VMA structure registered under the process context. The primary drawback of this linear structure is its high search latency, making it ideal only for scenarios that mandate a full sweep across all VMAs.

When a new process is created within the system, a corresponding anon_vma_chain (AVC) bridge structure is instantiated and bound directly to the process's local VMA structure. When this process subsequently forks a child process, it invokes the routine dup_mmap() to clone the VMA structures (for deeper analysis, developers can consult the implementation flow encompassing kernel_clone(), fork_idle(), copy_process(), copy_mm(), dup_mm(), and dup_mmap() within the source file git/kernel/fork.c). After cloning the parent process's VMA structures, the routine duplicates the parent's page table entries into the translation tables of the child process. This architectural optimization guarantees that the child process initially consumes no new backing physical memory. A fresh physical page block is allocated to the child process only when it generates a write transaction targeting the memory interval mapped by that VMA.

Following the VMA duplication stage, the kernel invokes anon_vma_fork(), which calls anon_vma_clone() to traverse the parent process's internal AVC linked list (anchored at the list head anon_vma_chain). For each AVC encountered during this sweep, a corresponding AVC structure is instantiated for the child context. The newly created AVC is populated with the parent's matching anon_vma reference alongside the child's newly cloned VMA reference. Following this configuration, the routine appends this new AVC instance onto the list headed by the child VMA's anon_vma_chain field, and inserts it into the interval red-black tree rooted at the anon_vma's rb_root field. This multi-stage cloning pipeline replicates the parent's anon_vma tracking chains over to the child process context. The explicit technical purpose of this setup is to establish an appropriate anon_vma mapping relationship for the child's new VMA, enabling the parent and child processes to share the underlying anonymous physical page frames while seamlessly supporting Copy-on-Write (CoW) exceptions and rmap reverse lookups.

This specific list is threaded together sequentially via the same_vma field. Figure 15-16 illustrates the interval red-black tree rooted at the anon_vma structure's rb_root field, which aggregates all AVC elements mapped under its jurisdiction. This binary search tree scales dynamically as a byproduct of process fork cycles, and the attached AVC elements map back to all VMAs across different address spaces that intersect this root anon_vma node. The structural interconnections among the VMA, AVC, and AV descriptors can be visualized as an intersection network in Figure 15-18. Here, the AVC functions analogously to an intersection switch array, establishing a flexible, clean many-to-many relationship mapping between individual VMAs and anon_vma contexts.

The programmatic routines responsible for identifying every virtual memory region mapping a common physical page frame are encapsulated inside central reverse mapping handlers such as page_referenced_anon(). Its standardized execution logic is executed as follows:

  • Extracting the target anon_vma from the physical page descriptor (page->mapping):
    The page->mapping pointer of an anonymous physical page frame does not link directly to a filesystem inode; instead, it points to the managing anon_vma structural backbone.

  • Traversing each individual AVC element hosted inside the anon_vma interval red-black tree:
    The kernel iterates over the tree entries to step through the intersecting references.

  • Resolving the specific VMA linked to each candidate AVC:
    The routine extracts a valid VMA mapping that shares access to that physical page block.

By continuously traversing all AVC entities attached to the anon_vma interval red-black tree, the memory subsystem can resolve every virtual memory area mapping that identical physical page block.

Beyond its role in orchestrating basic reverse memory mappings, this interval red-black tree—rooted at the anon_vma's rb_root field—is leveraged by the Kernel Same-page Merging (KSM) subsystem. The KSM engine scans the tree structure to evaluate identical physical memory pages that are eligible to be safely consolidated into a single shared page to optimize the system's memory footprint.

15.4.3 Mapping Anonymous Memory to Caching Buffers

Mapping anonymous memory to caching buffers involves designating a specified virtual memory range as a cache block. Following initial parameter compliance validations, the primary technical objective of this routine is to initialize the diverse fields of the vm_area_struct (VMA) container, aligning the VMA with the targeted memory area and ensuring it satisfies all required protection and operational attributes. Figure 15-19 illustrates the systematic workflow for mapping a specified memory region into a caching buffer.

Throughout this mapping procedure, the subsystem often needs to search through existing VMAs to determine whether the starting address of the designated region already resides within a virtual memory space allocated to another VMA. This lookup tracking sequence traverses the global red-black tree (whose root is anchored at the vm_rb field) managed within the process's mm_struct. It compares the target starting virtual address address against the vm_start and vm_end boundary flags of each VMA encountered during the tree walk. If the comparison satisfies the condition vma->vm_start <= address < vma->vm_end, it indicates that the virtual memory space managed by that specific VMA encapsulates the target starting address. 15.4.4 Mapping File-Backed Memory to Caching Buffers

File-backed memory is utilized to cache disk files into designated regions of physical memory. Because disk files, unlike anonymous memory, do not natively reside within the virtual address space, the operating system must employ a specialized mechanism to link disk files with virtual memory. This linkage is achieved via the address space structure (struct address_space), which is defined within the header file git/include/linux/fs.h. The address space structure works in tandem with the kernel-space file descriptor (struct file) and the index node structure (struct inode) to accomplish the mapping of disk files into the virtual memory space.

The address space structure defines objects that can be cached and mapped. It encloses multiple tracking fields, including the host object owning this structure (either an inode or a block storage device) and the total number of cached pages. It also encapsulates up to 22 operational callbacks, such as writing pages, reading pages, setting dirty page flags, page isolation, and page migration. Among these, the field responsible for tracking mapping relationships is i_mmap. This field serves as the root of an interval red-black tree composed of all VMAs cached within this memory buffer. The VMA nodes within this binary tree are threaded together via the shared.rb node member enclosed within each vm_area_struct. During the execution of a file-backed mapping, the system invokes the function vma_link_file() to insert the VMA node into this red-black tree, thereby binding the file to the VMA. Utilizing this binary tree allows the kernel to query the VMAs corresponding to a specific file and determine the mapped addresses of the file within the backing memory buffer. Figure 15-21 illustrates the interval red-black tree utilized for this caching mechanism.

Another highly critical field inside the address space structure is i_pages. This field is implemented as an extensible array (XArray), which encapsulates the descriptors of all cached physical pages (in kernel versions 5.15 and earlier; newer versions store pointers to struct folio data structures instead). Utilizing the diverse helper functions provided by the XArray subsystem, the kernel can directly perform read, write, and flag modification operations on the cached page descriptors using the index field of the physical page frames.

The kernel-space file descriptor (struct file) describes files that have been opened within the system, supporting user-space operations such as opening, reading, writing, and closing files via functions like fopen(). This structure encompasses fields including the file path structure f_path, a pointer to the index node structure f_inode, and a pointer to the address space structure f_mapping. It also specifies an operational method table via f_op, which defines handlers for file operations such as open, close, read, write, position querying (llseek), memory mapping (mmap), and retrieving unmapped areas (get_unmapped_area). The explicit components leveraged for cache mapping are f_mapping, f_inode, the mmap() method, and the get_unmapped_area() method. The mmap() method is responsible for mapping the file into the targeted VMA, while get_unmapped_area() is utilized to resolve an available unallocated starting address within the virtual memory space.

The index node structure (struct inode) stores file metadata and serves as the primary repository for file diagnostics within Linux. It records extensive data including the file mode, User ID (uid), Group ID (gid), file size, file type, file modification time, last access time, several pointers referencing underlying disk blocks, and general administrative metadata. It also exposes localized methods for manipulating the file and the index node structure itself. The actual raw data contents of the file are not preserved inside the inode. The methods for executing file operations utilize the handlers exposed by the file descriptor, whereas the methods for manipulating the index node structure primarily encompass directory table lookups, link(), unlink(), mknod(), rmnode(), mkdir(), rmdir(), and setattr(). The specific field within the index node structure utilized for memory mapping is i_mapping, which acts as a pointer targeting the explicit address_space structure. 15.4.5 Reverse Mapping from Physical Addresses to Virtual Memory Addresses

Due to process forking and memory sharing, a single physical page may be concurrently mapped to multiple distinct virtual addresses. Figure 15-23 illustrates a scenario where, through a multi-generational process tree, a single physical memory page is mapped to three different virtual memory regions. When a child process is forked, it bridges multiple translation domains: its local VMA's anon_vma_chain links both to the parent's inherited anon_vma (utilized for reverse-mapping older, shared pages) and to a fresh, dedicated anon_vma instantiated specifically for the child during the fork() lifecycle (utilized for tracking future exclusive pages).

As established in the preceding sections, forward address translation relies on navigating the page tables; by evaluating a virtual address through the page table entries (PTEs), the system resolves the matching physical Page Frame Number (PFN) along with its corresponding physical page descriptor (struct page). Conversely, reverse mapping (rmap) denotes the inverse process of tracing from a physical page descriptor back to its referencing virtual addresses. Because page tables are strictly unidirectional routing structures, even in the simplest scenario where a physical page maps to exactly one virtual memory page, the system cannot directly extract the mapped virtual address or the governing PTE from the struct page alone. This bottleneck is magnified because a single physical page frame can be simultaneously mapped to multiple virtual pages across distinct process address spaces. This reverse lookup capability is a mandatory prerequisite when the memory subsystem evicts page content out to the swap partition or releases physical pages back to the allocator.

In kernel versions prior to Linux 2.4, executing a reverse lookup required the system to traverse the page tables of every single process running in the system to identify all PTEs mapping a target physical address—a brute-force scanning pipeline that was exceptionally time-consuming. To resolve this architectural bottleneck, Rik Van Riel pioneered the conceptual framework of reverse mapping and proposed adding direct pointer networks to realize the lookups. However, Rik's initial design introduced significant memory overhead and proved suboptimal for production scaling.

To refine this approach, Dave McCracken introduced object-based reverse mapping. This method was primarily tailored for file-backed memory reverse lookups, and the mmap() system call architecture leverages this paradigm. For a file-backed mapping, Dave enabled object-based rmap by routing the physical page descriptor's mapping pointer to reference its parent address_space structure.

However, for anonymous mappings, the struct page's mapping field initially remained unassigned. To extend reverse mapping capabilities to anonymous memory domains, Andrea Arcangeli proposed routing the mapping field to reference a target VMA directly. Yet, this simple relationship broke down during process replication: when a process forks, a single inherited VMA maps to multiple disjoint page table domains across different address spaces, meaning a single physical address maps to multiple distinct virtual addresses. Consequently, mapping anonymous memory via a direct, singular pointer from page->mapping to a VMA was architecturally unviable.

To overcome this structural barrier, Andrea defined the anon_vma (AV) and anon_vma_chain (AVC) structures. Each process utilizes AVC bridge elements to bind its local VMA instances to the appropriate anon_vma contexts. Via the unified anon_vma_chain linked lists, a process simultaneously tracks the shared anonymous pages inherited from its parent ancestry alongside its own exclusive, locally generated anonymous pages. The definitive structural mechanics of these tracking meshes have been detailed across the preceding sections introducing the AV and AVC subsystems.

15.4.6 Reverse Mapping from Anonymous Memory to Virtual Memory

During anonymous memory mapping, the mapping field of the physical page descriptor points directly to its corresponding anon_vma structure. To execute a reverse mapping lookup, the system leverages this mapping pointer to resolve the target anon_vma context and accesses the interval red-black tree rooted at its rb_root field. By traversing the individual anon_vma_chain (AVC) entries within this binary search tree, the kernel can identify all VMAs that map this specific physical page descriptor page, thereby resolving every referencing virtual memory page across the system. Furthermore, by evaluating the index field of the page structure, the engine determines the exact page offset within the virtual address space managed by each VMA. 15.4.7 Reverse Mapping from Files to Memory

As established previously, Dave McCracken enabled reverse mapping for file-backed memory by routing the mapping field of the physical page descriptor to point directly to its parent address space structure. The system leverages the physical page descriptor's mapping field to locate the corresponding address_space structure. Via the i_mmap pointer of this address space structure, the engine accesses the interval red-black tree composed of all referencing VMAs. By traversing the diverse VMA nodes within this binary tree, the system resolves every VMA mapping that specific physical page frame, and subsequently tracks back to the target physical file descriptor via the VMA's vm_file field.
